# ISO/IEC 25010 Quality Assessment

## Standard application

This project uses ISO/IEC 25010 product-quality characteristics as an assessment framework for selecting evidence and discussing risks. It is not ISO-certified, and these tests do not establish conformity or certification. this matrix uses the commonly taught product-quality characteristics.

## Characteristics mapped to evidence

| Characteristic | SGR quality question | Demonstration evidence | Current limitation / next action |
|---|---|---|---|
| Functional suitability | Does the system provide correct Golden Path functions and outputs? | `GoldenPathSystemTest`; capacity, eligibility, payment, hectares, delivery/recovery assertions; UI acceptance script. | Legacy record models/APIs remain alongside the Golden Path models; explain the API path used in the demo. |
| Performance efficiency | Does the read-only API respond acceptably under a stated small workload? | `performance_smoke.py` reports requests/sec, median and p95 for a stated request count/concurrency. | Not a stress/load/capacity result. Agree threshold and workload; run only local synthetic data. |
| Compatibility | Do frontend and backend communicate under the expected local origins? | Browser flow at configured Vite origins; Django CORS configuration; production frontend build. | Browser support matrix is not automated. Demonstrate the actual browser/runtime used. |
| Usability / interaction capability | Can an operator complete common tasks and understand validation/error states? | Live UI acceptance script: search, form entry, duplicate-ID error, dropdown choices, status and details. | Manual observation only; capture lecturer feedback or usability notes. |
| Reliability | Does the system behave consistently and preserve derived data through a workflow? | Full Golden Path integration/system test, transaction rollback checks, repeatable geography seed tests, regression runner. | No long-duration uptime/recovery or database-failure test. |
| Security | Are identities, roles, scope and data protected? | Login/invalid/expired JWT tests, role denials, district read/write scoping, ZAP passive report. | ZAP baseline is unauthenticated passive scanning. It does not prove all RBAC paths or replace an authorized active assessment. |
| Maintainability | Can changes be checked and defects localized? | pytest tests, statement/branch coverage, ESLint JSON, Django migration drift check. | Coverage percentage is not a quality score and current branch coverage is incomplete. |
| Portability | Can the code be built/run from documented dependencies and configuration? | backend venv commands, frontend npm build, environment-based settings, reproducible scripts. | Only the current Linux/local SQLite demonstration configuration has been exercised. |

## ISO 9001 process practices used (supporting evidence, not a claim of certification)

- Requirements and test cases are linked in `TEST_PLAN.md`.
- Repeatable test execution and generated records are provided by `run_checks.sh`.
- Defects have a status, severity, reproduction, correction and retest entry in `DEFECT_LOG.md`.
- Measurement outputs are preserved as JUnit, coverage and lint artifacts.
- Corrective action is demonstrated by fixing a reproducible defect and rerunning its focused test and regression suite.

Do not say “the application is ISO compliant/certified.” Say: “We used ISO/IEC 25010 characteristics to structure product-quality evaluation and documented an ISO 9001-style evidence/corrective-action process.”
